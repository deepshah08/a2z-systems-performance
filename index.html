Part I

CPU Scheduling & Microarchitecture

How the Linux kernel shares physical CPU cores among thousands of threads. Completely Fair Scheduling math, context switch penalties, and hardware performance monitoring units.

01 Scheduler Math

Completely Fair Scheduler (CFS) & vruntime Red-Black Tree

The Linux Completely Fair Scheduler (CFS) models an "ideal multi-tasking CPU" on hardware. Instead of traditional fixed time slices, CFS tracks the virtual runtime (vruntime) of each runnable task. Tasks are stored in a self-balancing Red-Black Tree keyed by vruntime.

When a CPU core finishes executing a quantum, the kernel picks the leftmost task in the tree (the task that has consumed the least proportional execution time). When task $i$ runs for physical time $\Delta_{\text{exec}}$, its virtual runtime advances according to its nice level weight:

$$\Delta vruntime = \Delta_{\text{exec}} \times \frac{W_{\text{NICE\_0}}}{W_i}$$

Tasks with lower nice values (higher priority) have larger weights $W_i$, causing their vruntime to advance much slower—granting them significantly more CPU execution time!

02 CPU Overhead

Context Switching Latency, Runqueues & CPU Affinity

A context switch occurs when the kernel preempts a running process to execute another. Context switches fall into two distinct categories:

  • Voluntary Context Switches: The thread blocked waiting for an unavailable resource (e.g. disk I/O, network packet, mutex lock, or sleep()).
  • Involuntary Context Switches: The thread's allocated time quantum expired, or a higher-priority task woke up, forcing kernel preemption.

Switching between threads in the same process is relatively cheap ($\approx 300\text{--}500\text{ ns}$) because the virtual memory address space (mm_struct) remains unchanged. In contrast, switching between separate processes requires rewriting the CR3 register, invalidating CPU TLB entries and causing cold cache misses across L1 and L2 caches ($\approx 1.5\text{--}5\text{ }\mu\text{s}$).

03 PMU Profiling

Hardware Performance Counters (PMU) & Topdown Analysis

Modern microprocessors contain dedicated Performance Monitoring Units (PMUs) capable of counting low-level microarchitectural events (CPU cycles, instructions retired, cache misses, branch mispredictions) without software instrumentation overhead.

The industry-standard Topdown Microarchitecture Analysis Method (Ahmad Yasin, Intel) categorizes every pipeline execution slot into four mutually exclusive buckets:

  • Retiring (> 50% ideal): Slots executing instructions that successfully commit useful architectural state.
  • Bad Speculation: Slots wasted executing speculative instructions along mispredicted branch paths that were later discarded.
  • Frontend Bound: The CPU fetch and decode pipeline failed to deliver micro-ops to the execution engine.
  • Backend Bound: Execution units stalled waiting for memory operands (L3 LLC misses, DRAM latency) or functional unit resource contention.
04 cgroups v2

Linux CPU Throttling: CFS Bandwidth Control & cgroups v2

In containerized production environments (Kubernetes, Docker), CPU limits are enforced via cgroups CFS Bandwidth Control (cpu.max = quota period, typically quota / 100000). When a container consumes its entire quota before the end of the 100ms period, the Linux kernel completely suspends all container threads until the next period begins.

This causes catastrophic tail latency spikes (e.g. p99 jumping from 5ms to 80ms) even when average CPU utilization across the node is only 25%! Systems engineers monitor /sys/fs/cgroup/cpu.stat (nr_throttled and throttled_usec) to detect quota starvation.

Part II

Memory Subsystem & Paging

How Linux maps virtual address spaces to physical RAM. Page table walks, TLB shootdowns, copy-on-write page faults, and kernel page cache writeback.

05 Virtual Memory

Page Tables, Translation Lookaside Buffer & TLB Shootdowns

On x86_64 architecture, translating a 48-bit virtual address to a physical RAM address requires walking a 4-level hierarchical page table structure: PML4 $\rightarrow$ PDPT $\rightarrow$ PD $\rightarrow$ PT. A page walk costs up to 4 sequential DRAM reads ($\approx 150\text{--}200\text{ cycles}$).

The Translation Lookaside Buffer (TLB) caches these translations, delivering single-cycle address lookups. However, when a thread frees or remaps memory (via munmap() or compaction), the kernel must guarantee no other CPU core holds stale translations in its local TLB. The kernel initiates a TLB Shootdown, sending Inter-Processor Interrupts (IPIs) across the memory bus to stall all remote cores until they flush their local TLB entries.

06 Page Faults

The Page Fault Pipeline: Minor vs. Major Faults & RSS

When an application calls malloc() or mmap(), the kernel modifies the process Virtual Memory Area (VMA) but allocates zero physical memory. Physical RAM is allocated lazily on the first byte read or write, triggering a Hardware Page Fault interrupt:

  • Minor Page Fault: The requested page already resides in RAM (e.g. demand-zero allocation, shared library page in page cache, or Copy-on-Write page duplicate after fork()). Resolved purely in CPU kernel space in a few microseconds without disk I/O.
  • Major Page Fault: The requested page must be loaded from persistent storage (e.g. swapped-out memory page or unmapped executable binary sector). The calling thread is suspended into uninterruptible sleep (D state) for milliseconds until disk read completes.
07 Page Cache

Linux Page Cache Dynamics & Dirty Memory Writeback

The Linux Page Cache uses unallocated RAM to cache files read from and written to storage. When a process writes data, the kernel writes into page cache memory and marks the pages dirty, allowing the write() syscall to return instantly.

Background kernel threads (kworker/flush) periodically flush dirty pages to storage. The flush behavior is governed by two critical sysctl thresholds:

  • vm.dirty_background_ratio (default 10%): When dirty memory crosses this threshold, background kernel flush threads wake up to write data to disk asynchronously.
  • vm.dirty_ratio (default 20%): When dirty memory crosses this hard ceiling, user-space processes calling write() are frozen and forced into synchronous writeout until dirty memory drops below the threshold!
08 Kernel Memory

SLUB Allocator & Kernel Object Caching

While the kernel Buddy Allocator manages memory in coarse 4KB page frames, kernel internal data structures (such as task_struct, inode, dentry, and mm_struct) are typically only tens to hundreds of bytes. Allocating full 4KB pages would cause catastrophic internal memory fragmentation.

The Linux SLUB Allocator carves page frames into uniform object slots. Each slab maintains an in-line freelist pointer chain. Allocating an object requires popping the head pointer in $O(1)$ time without taking coarse page-allocator locks, guaranteeing warm L1/L2 cache locality for frequent kernel object lifecycles.

Part III

Block I/O & Modern Storage

How Linux handles storage input/output: the multi-queue block layer (blk-mq), lockless shared-memory rings in io_uring, and eBPF block latency profiling.

09 Block Layer

The Linux Block I/O Layer & Multi-Queue (blk-mq) Architecture

In traditional Linux kernels, all block I/O requests funneled through a single global request queue protected by a single lock—creating an impossible bottleneck on multi-core servers with high-speed SSDs. The modern Multi-Queue Block Layer (blk-mq) solves this with a two-tier queue hierarchy:

  • Software Staging Queues: Allocated per-CPU core, allowing threads to submit I/O requests concurrently with zero cross-core locking.
  • Hardware Dispatch Queues: Mapped directly to the multi-queue hardware submission queues of NVMe controllers.

I/O schedulers like mq-deadline and BFQ operate between these tiers, merging adjacent sectors to maximize sequential burst throughput.

10 Async I/O

Modern High-Throughput Linux I/O: io_uring Ring Buffers

Introduced by Jens Axboe in Linux 5.1, io_uring provides true zero-copy asynchronous I/O across storage files, network sockets, and timer events. Unlike legacy POSIX AIO or epoll, io_uring communicates via two lockless ring buffers mapped into shared memory between user-space and kernel:

  • Submission Queue (SQ): The application writes Submission Queue Entries (SQEs) to the ring buffer. In polling mode (IORING_SETUP_SQPOLL), a kernel thread reaps SQEs automatically—eliminating system call context switches entirely!
  • Completion Queue (CQ): The kernel posts Completion Queue Entries (CQEs) as hardware operations finish, ready for instant consumption by user space.
11 Latency Histograms

Disk Latency Profiles & eBPF biolatency Histograms

Average latency (such as reported by iostat) is notoriously deceptive: an average disk latency of 2ms can easily conceal a bimodal distribution where 99% of requests complete in 50 microseconds while 1% suffer 100ms controller garbage-collection stalls!

Using eBPF (Extended Berkeley Packet Filter) tools like Brendan Gregg's biolatency, engineers instrument the kernel block layer at zero runtime overhead. eBPF instruments the request issue and device completion tracepoints, recording request duration into in-kernel log2 histogram maps.

Part IV

Networking & Kernel Profiling

How Linux processes millions of packets per second, manages TCP buffer autotuning, verifies eBPF bytecode safety, and visualizes CPU stack profiles via Flame Graphs.

12 Network RX/TX

Linux Network RX Path: Ring Buffers, NAPI Polling & SoftIRQs

When high-speed network interfaces receive hundreds of thousands of packets per second, handling each packet with a dedicated hardware CPU interrupt triggers an Interrupt Storm, starving user-space applications of CPU cycles.

The Linux New API (NAPI) subsystem uses hybrid polling: the first packet triggers a hardware interrupt, which schedules the network softirq (net_rx_action) and immediately disables further hardware interrupts on the NIC. The kernel then polls and drains up to 64 packets per poll budget from the DMA ring buffer. If packets remain, the softirq daemon (ksoftirqd) continues processing without context switching into interrupt handlers.

13 TCP Tuning

Socket Buffers (sk_buff) & TCP Buffer Autotuning

To saturate high-speed long-distance network links, the TCP sliding window must equal or exceed the Bandwidth-Delay Product (BDP) of the connection:

$$\text{BDP} = \text{Bandwidth (bits/sec)} \times \text{Round-Trip Time (sec)}$$

If socket buffers (tcp_rmem and tcp_wmem) are capped smaller than the BDP, the sender will stall waiting for ACKs before filling the physical bandwidth capacity of the link. Linux dynamic TCP buffer autotuning automatically expands socket receive and send windows up to configured maximum limits to match active network BDP.

14 Kernel Programmability

eBPF Architecture: Verifier, JIT Compiler & Kernel Maps

eBPF (Extended Berkeley Packet Filter) is an in-kernel virtual machine that allows running sandboxed user-written bytecode directly inside the Linux kernel without modifying kernel source code or loading risky kernel modules.

Before any eBPF program is loaded, the kernel passes it through the eBPF Verifier. The verifier traverses the Directed Acyclic Graph (DAG) of all possible code paths, proving mathematical invariants: the program must terminate (no unbounded loops), must not dereference uninitialized or out-of-bounds pointers, and must not leak kernel memory. Once verified, an in-kernel JIT compiler converts the bytecode into native machine code.

15 Visualization

Profiling with Flame Graphs: On-CPU vs. Off-CPU Analysis

Invented by Brendan Gregg, Flame Graphs are the premier visualization for systems performance profiling. Stack traces are sampled (e.g. via perf record -F 99 -g), folded into aggregated hierarchies, and rendered as stacked rectangles:

  • X-axis: Represents the entire sample population sorted alphabetically (not passage of time). The wider a box, the more frequently that function was on the stack.
  • Y-axis: Shows stack depth. The top-most boxes represent the functions actively executing at sample time.

Crucially, On-CPU profiling reveals compute churn and algorithmic bottlenecks, while Off-CPU profiling (measuring time spent blocked in schedule()) reveals lock contention, file I/O delays, and network socket stalls!
